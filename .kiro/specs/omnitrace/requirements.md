# Requirements Document

## Introduction

OmniTrace is an AI-powered autonomous incident detection and remediation platform targeting a reduction in Mean Time to Detect (MTTD) and Mean Time to Resolve (MTTR) from 45+ minutes to under 30 seconds. The system ingests operational events via Amazon EventBridge, orchestrates three AWS Lambda-based AI agents (Auditor, Patcher, Validator) through an AWS Step Functions state machine, executes or escalates remediations based on risk tier, and exposes incident telemetry through a React/Tailwind/Vite dashboard hosted on AWS Amplify. All cost savings are denominated in INR. A built-in anomaly simulator injects synthetic fault events to enable end-to-end testing without real incidents.

---

## Glossary

- **Auditor**: AWS Lambda agent that performs root cause analysis (RCA) using `anthropic.claude-3-5-sonnet` via Amazon Bedrock.
- **Patcher**: AWS Lambda agent that generates and executes remediation scripts using `amazon.nova-pro-v1:0` via Amazon Bedrock.
- **Validator**: AWS Lambda agent that performs guardrail safety checks on proposed remediations using `amazon.nova-pro-v1:0` via Amazon Bedrock.
- **Orchestrator**: AWS Step Functions ASL state machine that coordinates the Auditor → Validator → Patcher pipeline.
- **Incident**: A detected operational anomaly represented as a DynamoDB record identified by IncidentID and Timestamp.
- **Remediation**: A corrective action (cache purge, container restart, scale-out, rollback, DB change) generated by the Patcher and validated by the Validator.
- **Risk Tier**: Classification of a remediation action as Low-risk, Medium-risk, or High-risk, determining the approval and execution path.
- **Dashboard**: React + Tailwind CSS + Vite single-page application hosted on AWS Amplify that displays incident status, agent traces, cost savings, and one-click approval controls.
- **Simulator**: AWS Lambda function that injects synthetic anomaly events (latency spikes, 5xx errors, memory OOM) into EventBridge.
- **SRE**: Site Reliability Engineer; the escalation recipient for High-risk remediations via SNS.
- **MTTD**: Mean Time to Detect — elapsed time between fault occurrence and detection.
- **MTTR**: Mean Time to Resolve — elapsed time between detection and confirmed resolution.
- **INR**: Indian Rupee; the denomination for all cost-savings metrics stored and displayed by the system.
- **SSM**: AWS Systems Manager; used to execute remediation commands on target compute resources.
- **SNS**: Amazon Simple Notification Service; used for SRE escalation alerts.
- **EventBridge**: Amazon EventBridge; the entry point for all incident events.
- **Single-Table**: DynamoDB table design using IncidentID (partition key) and Timestamp (sort key) with attributes AgentTraces, Status, and CostSavedINR.

## Requirements

### Requirement 1 — Event Ingestion

**User Story:** As an SRE, I want all operational anomaly events to arrive at a single, well-defined entry point, so that the detection pipeline begins deterministically without manual intervention.

#### Acceptance Criteria

1. THE EventBridge SHALL accept incident events conforming to a defined JSON schema containing at minimum: `source`, `detail-type`, `detail.incidentId`, `detail.faultType`, and `detail.timestamp`.
2. WHEN an event matching the OmniTrace event rule is received by EventBridge, THE Orchestrator SHALL be triggered within 5 seconds.
3. IF an event fails schema validation, THEN THE EventBridge SHALL route the event to a dead-letter queue and THE system SHALL log the validation failure to CloudWatch Logs.
4. THE EventBridge SHALL support at least three fault event types: `LatencySpike`, `HTTP5xxError`, and `MemoryOOM`.

---

### Requirement 2 — Orchestration

**User Story:** As a platform engineer, I want a durable state machine to coordinate the multi-agent pipeline, so that each step is auditable, retryable, and observable.

#### Acceptance Criteria

1. THE Orchestrator SHALL execute agent steps in the order: Auditor → Validator → Patcher.
2. WHEN any agent step returns a non-success status, THE Orchestrator SHALL retry the step up to 2 times with exponential back-off before transitioning to a failure state.
3. WHEN all agent steps succeed, THE Orchestrator SHALL update the Incident record status to `RESOLVED` in DynamoDB.
4. WHEN the Orchestrator transitions to a failure state, THE Orchestrator SHALL update the Incident record status to `FAILED` and publish a failure notification to the SNS escalation topic.
5. THE Orchestrator SHALL record the ARN and execution name of every Step Functions execution in the DynamoDB Incident record under `AgentTraces`.
6. WHILE an execution is in progress, THE Orchestrator SHALL maintain execution state in Step Functions so that the execution is resumable after a Lambda timeout.

---

### Requirement 3 — Auditor Agent (RCA)

**User Story:** As an SRE, I want an AI agent to automatically determine the root cause of an incident, so that I receive a structured diagnosis without spending time on manual log analysis.

#### Acceptance Criteria

1. WHEN the Orchestrator invokes the Auditor, THE Auditor SHALL query CloudWatch Logs for log events related to the incident within the preceding 15-minute window.
2. THE Auditor SHALL invoke the `anthropic.claude-3-5-sonnet` model via Amazon Bedrock to generate a root cause analysis.
3. WHEN the Bedrock invocation succeeds, THE Auditor SHALL return a structured RCA payload containing: `rootCause` (string), `confidence` (0.0–1.0), and `recommendedActions` (array of strings).
4. IF the Bedrock invocation returns an error, THEN THE Auditor SHALL throw a retryable exception so that the Orchestrator retry policy is triggered.
5. THE Auditor SHALL complete its execution within 60 seconds to stay within Step Functions task timeout bounds.

---

### Requirement 4 — Validator Agent (Guardrail Safety Checks)

**User Story:** As a platform engineer, I want every proposed remediation to be safety-checked before execution, so that automated actions do not cause additional harm.

#### Acceptance Criteria

1. WHEN the Orchestrator invokes the Validator, THE Validator SHALL receive the Patcher's proposed remediation plan as input.
2. THE Validator SHALL invoke the `amazon.nova-pro-v1:0` model via Amazon Bedrock to assess the safety of the proposed remediation.
3. WHEN the safety assessment is complete, THE Validator SHALL return a `riskTier` value of `LOW`, `MEDIUM`, or `HIGH` and a `safetyScore` (0.0–1.0).
4. IF the Bedrock invocation returns an error, THEN THE Validator SHALL throw a retryable exception so that the Orchestrator retry policy is triggered.
5. THE Validator SHALL complete its execution within 45 seconds.

---

### Requirement 5 — Patcher Agent (Remediation Execution)

**User Story:** As an SRE, I want the system to automatically generate and execute remediations, so that incidents are resolved without manual intervention wherever safe to do so.

#### Acceptance Criteria

1. WHEN the Orchestrator invokes the Patcher, THE Patcher SHALL invoke the `amazon.nova-pro-v1:0` model via Amazon Bedrock to generate a remediation script appropriate to the incident's fault type.
2. WHEN the Validator returns `riskTier` of `LOW`, THE Patcher SHALL execute the remediation via AWS SSM and publish a notification to the SNS notification topic confirming auto-application.
3. WHEN the Validator returns `riskTier` of `MEDIUM`, THE Patcher SHALL write the remediation plan to DynamoDB with status `PENDING_APPROVAL` and SHALL NOT execute the remediation autonomously.
4. WHEN the Validator returns `riskTier` of `HIGH`, THE Patcher SHALL publish an escalation message to the SNS SRE topic containing the incident ID, RCA summary, and proposed remediation details, and SHALL NOT execute the remediation autonomously.
5. IF the SSM execution for a `LOW` risk remediation returns a non-zero exit code, THEN THE Patcher SHALL mark the remediation status as `EXECUTION_FAILED` in DynamoDB and trigger the Orchestrator failure path.
6. THE Patcher SHALL complete its execution within 90 seconds.

---

### Requirement 6 — Data Persistence

**User Story:** As an SRE, I want every incident and its full agent trace stored durably, so that I can audit past incidents and measure cost savings over time.

#### Acceptance Criteria

1. THE DynamoDB Single-Table SHALL use `IncidentID` as the partition key and `Timestamp` as the sort key.
2. WHEN a new incident event is received, THE system SHALL create a DynamoDB record containing: `IncidentID`, `Timestamp`, `Status` (initial value `OPEN`), `AgentTraces` (initial value empty list), and `CostSavedINR` (initial value `0`).
3. WHEN an incident is resolved, THE system SHALL update `Status` to `RESOLVED` and SHALL store the computed cost savings in `CostSavedINR` as a numeric value in Indian Rupees.
4. THE DynamoDB table SHALL have point-in-time recovery (PITR) enabled.
5. THE DynamoDB table SHALL have a TTL attribute `ExpiresAt` set to 90 days from incident creation, after which records expire automatically.

---

### Requirement 7 — Risk-Tiered Remediation Approval

**User Story:** As an SRE, I want different approval workflows for different risk levels, so that low-risk fixes happen instantly while high-risk changes require human sign-off.

#### Acceptance Criteria

1. WHEN a `LOW` risk remediation is auto-applied, THE system SHALL send a notification via SNS containing the incident ID, remediation type, and execution result within 30 seconds of the Patcher completing.
2. WHEN a `MEDIUM` risk remediation is pending, THE Dashboard SHALL display an approval button for the incident within 5 seconds of the DynamoDB record reaching `PENDING_APPROVAL` status.
3. WHEN an SRE clicks the approval button on the Dashboard for a `MEDIUM` risk remediation, THE API Gateway SHALL receive the approval request and THE Orchestrator SHALL resume execution of the Patcher within 10 seconds.
4. WHEN a `HIGH` risk incident is escalated, THE SNS SRE topic SHALL deliver the escalation message containing incident ID, RCA summary, and remediation proposal to all subscribed SRE endpoints.
5. THE system SHALL not execute a `HIGH` risk remediation without explicit out-of-band SRE confirmation.

---

### Requirement 8 — Dashboard (Frontend)

**User Story:** As an SRE, I want a live web dashboard to monitor incidents, approve medium-risk remediations, and review cost savings, so that I have full situational awareness without using the AWS console.

#### Acceptance Criteria

1. THE Dashboard SHALL be deployed and served via AWS Amplify Hosting with CI/CD triggered by commits to the designated repository branch.
2. THE Dashboard SHALL display a list of all incidents with their `IncidentID`, `Timestamp`, `Status`, and `CostSavedINR` values, refreshed at most every 10 seconds.
3. WHEN an incident has `Status` of `PENDING_APPROVAL`, THE Dashboard SHALL render a one-click approval button associated with that incident.
4. THE Dashboard SHALL display agent trace details for a selected incident, including the Auditor's `rootCause` and `confidence` values.
5. THE Dashboard SHALL display aggregate cost savings in INR across all resolved incidents for the current calendar month.
6. THE Dashboard SHALL be built using React, Tailwind CSS, and Vite.
7. IF the API Gateway returns a non-2xx response, THEN THE Dashboard SHALL display a human-readable error message and SHALL NOT leave the user with a blank or broken view.

---

### Requirement 9 — API Gateway

**User Story:** As a frontend developer, I want a RESTful API to back the dashboard, so that incident data and approval actions can be performed over standard HTTP.

#### Acceptance Criteria

1. THE API Gateway SHALL expose a `GET /incidents` endpoint that returns a paginated list of incident records from DynamoDB.
2. THE API Gateway SHALL expose a `GET /incidents/{incidentId}` endpoint that returns the full record for a single incident including `AgentTraces`.
3. THE API Gateway SHALL expose a `POST /incidents/{incidentId}/approve` endpoint that resumes the Step Functions execution for a `PENDING_APPROVAL` incident.
4. WHEN the `POST /incidents/{incidentId}/approve` endpoint is called for an incident not in `PENDING_APPROVAL` status, THE API Gateway SHALL return HTTP 409 with an error body describing the conflict.
5. THE API Gateway SHALL require authentication via AWS IAM or Amazon Cognito on all endpoints.
6. IF any API Gateway Lambda integration returns an unhandled exception, THEN THE API Gateway SHALL return HTTP 500 with a generic error message and SHALL log the full exception to CloudWatch Logs.

---

### Requirement 10 — Anomaly Simulator

**User Story:** As a developer, I want a built-in simulator to inject synthetic fault events, so that I can exercise the full incident pipeline without waiting for real production anomalies.

#### Acceptance Criteria

1. THE Simulator SHALL be an AWS Lambda function invocable on-demand via the API Gateway or AWS console.
2. THE Simulator SHALL support injection of at least three synthetic event types: `LatencySpike`, `HTTP5xxError`, and `MemoryOOM`.
3. WHEN the Simulator is invoked with a valid event type, THE Simulator SHALL publish a correctly-structured EventBridge event that triggers the OmniTrace event rule.
4. WHEN the Simulator is invoked with an invalid or unsupported event type, THE Simulator SHALL return HTTP 400 with a descriptive error message and SHALL NOT publish an event to EventBridge.
5. THE Simulator SHALL include configurable parameters for `severity` (low, medium, high) and `targetService` (string) within the synthetic event payload.

---

### Requirement 11 — Observability

**User Story:** As an SRE, I want centralised logs and metrics for all system components, so that I can diagnose failures in the OmniTrace platform itself.

#### Acceptance Criteria

1. THE system SHALL emit structured JSON logs to CloudWatch Logs for every Lambda invocation, including at minimum: `incidentId`, `agentName`, `durationMs`, `status`, and `errorDetails` (null when no error).
2. THE system SHALL publish a CloudWatch metric `IncidentResolutionTimeMs` for each resolved incident, representing the elapsed time from EventBridge ingestion to `RESOLVED` status.
3. WHEN `IncidentResolutionTimeMs` exceeds 30,000 milliseconds (30 seconds), THE system SHALL publish a CloudWatch alarm to the SNS notification topic.
4. THE system SHALL publish a CloudWatch metric `RemediationCostSavedINR` for each resolved incident using the value stored in DynamoDB.
5. THE Step Functions execution history SHALL be retained for 90 days to support incident post-mortems.

---

### Requirement 12 — Security and IAM

**User Story:** As a security engineer, I want every component to operate under least-privilege IAM roles, so that a compromised component cannot affect resources outside its scope.

#### Acceptance Criteria

1. THE Auditor Lambda SHALL have an IAM role granting read-only access to CloudWatch Logs and permission to invoke only the `anthropic.claude-3-5-sonnet` Bedrock model.
2. THE Patcher Lambda SHALL have an IAM role granting write access to DynamoDB, permission to invoke only the `amazon.nova-pro-v1:0` Bedrock model, permission to publish to the designated SNS topics, and permission to send SSM commands to tagged compute resources.
3. THE Validator Lambda SHALL have an IAM role granting read access to DynamoDB and permission to invoke only the `amazon.nova-pro-v1:0` Bedrock model.
4. THE Orchestrator (Step Functions) SHALL have an IAM role permitting invocation of the Auditor, Patcher, and Validator Lambda functions and read/write access to the DynamoDB Single-Table.
5. THE API Gateway SHALL enforce authentication on all routes so that unauthenticated requests receive HTTP 401.
6. IF a Lambda function's IAM role is modified to grant permissions beyond its defined scope, THEN THE system SHALL detect the change via AWS Config and publish an alert to the SNS notification topic.
